# Project AGENTS Rules — STM32 Embedded Architecture & Firmware

> **Board/MCU:** STM32 Series (STM32F411xE / ARM Cortex-M4 with FPU)  
> **Framework:** STM32Cube HAL & LL Drivers + CMSIS  
> **Build System:** CMake (Presets: Debug, Release) + Ninja + ARM GNU Toolchain (`arm-none-eabi-gcc`)  
> **Flash/Debug Tool:** STM32CubeProgrammer CLI (`STM32_Programmer_CLI`) / ST-Link / OpenOCD  
> **IDE:** Antigravity (primary)  
> **Repo:** Git-managed monorepo  

---

## 1. Requirement Alignment — Mandatory Before Code Generation

**RULE: Never generate code without first aligning requirements.**

Before implementing any feature or making any architectural change:

1. **Use `/grill-me`** — Run a structured interview to resolve ambiguity, clarify design decisions, peripheral mapping, and lock requirements. Minimum 3 rounds of questions before proceeding.
2. **For new features** — Write a PRD (Product Requirements Document) or implementation plan artifact (`/write-a-prd`). Get explicit user approval before coding.
3. **For bug fixes** — State the root cause hypothesis, proposed fix, and verification method. Get confirmation before implementing.
4. **For refactors** — Justify the refactor with measurable benefits (reduced complexity, better testability, lower context cost).

### Interview Structure (grill-me pattern)
```text
Stage 1: Hardware context — STM32 chip, pinout, clock tree, peripherals (TIM, USART, SPI, I2C, DMA)
Stage 2: Requirements — What must it do, what must it NOT do, throughput/latency limits
Stage 3: Concurrency — Bare-metal super-loop / state machine vs FreeRTOS (CMSIS-RTOS v2)
Stage 4: Interface design — Public API in Core/User/<module>/, return codes (HAL_StatusTypeDef / bool)
Stage 5: Verification — CMake build check, Cppcheck static analysis, hardware flashing & logic proof
```

## 2. Multi-Agent Role Separation

When working on complex tasks, operate in three distinct phases:

### Planner Role
- Research codebase, dependencies, and implications.
- Create `implementation_plan.md` artifact.
- **NO code changes** — only analysis and design.
- Identify risks, open questions, breaking changes.
- Request user review before proceeding.

### Coder Role
- Execute the approved plan.
- Create/modify files following the Deep Module pattern in `Core/User/`.
- Respect STM32CubeMX generated code sections (`USER CODE BEGIN` / `USER CODE END`).
- Track progress in `task.md` artifact.
- Commit logical units of work.

### Reviewer Role
- Run automated tests (`cppcheck` for C code, local unit tests).
- Verify firmware compilation via `cmake --build build/Debug`.
- Verify the implementation matches the approved plan.
- Check for regressions, buffer overflows, interrupt race conditions.
- Create `walkthrough.md` summarizing what was done.

## 3. Deep Module Architecture

**RULE: Minimize public interface surface. Maximize internal depth.**

Every custom module must follow this pattern:

### For Embedded C (`Core/User/<module>/`)
```text
Core/User/<module_name>/
├── <module_name>.h   # PUBLIC: Minimal function declarations (3-7 functions max)
└── <module_name>.c   # PRIVATE: Full implementation, static functions, static state
```

- **Header files (`.h`):** Only expose init/process/deinit + essential types.
- **Implementation (`.c`):** Use `static` for all internal functions.
- **No global variables:** Use module-scoped `static` structs.
- **Fixed-size buffers:** Compile-time constants preferred over dynamic allocation.

### Context Cost Rule
If an AI agent needs to read more than 2 files to understand a module's interface, the module is too leaky. Refactor it.

## 4. Embedded C Coding Standards (STM32 & Cortex-M4)

### Naming Conventions
```c
// Functions: module_prefix + verb + noun
void ring_buffer_init(ring_buffer_t *rb);
bool ring_buffer_push(ring_buffer_t *rb, uint8_t data);
bool ring_buffer_pop(ring_buffer_t *rb, uint8_t *data);

// Types: PascalCase or snake_case with _t suffix
typedef struct ring_buffer_t { ... } ring_buffer_t;

// Constants / Macros: UPPER_SNAKE_CASE
#define RING_BUFFER_SIZE  64

// Static (private): prefix with underscore or declare static
static void _reset_indices(ring_buffer_t *rb);
```

### STM32CubeMX Regeneration Safety
- **NEVER** edit files inside `cmake/stm32cubemx/` — this directory is wiped and regenerated by STM32CubeMX.
- In `Core/Src/main.c`, `Core/Src/stm32f4xx_it.c`, etc., **ONLY** insert custom code inside comment blocks:
  ```c
  /* USER CODE BEGIN ... */
  // Your code here
  /* USER CODE END ... */
  ```
- **Place all new features and business logic** in dedicated folders under `Core/User/<feature>/`.

### Memory & Safety
- **Zero dynamic memory allocation:** No `malloc()`, `calloc()`, `free()`. Use static allocation only.
- All buffers must have compile-time explicit size bounds (`#define BUFFER_SIZE ...`).
- Check return values from all HAL/LL driver calls (`HAL_StatusTypeDef`).
- Assert critical invariants with `assert_param()` or custom software asserts.

### Interrupt Safety & Concurrency
- Keep ISR handlers minimal: clear interrupt flag, set volatile flag / ring buffer push, and exit.
- Shared variables accessed in both ISR and background code must be marked `volatile`.
- Protect critical sections using CMSIS primitives:
  ```c
  uint32_t primask = __get_PRIMASK();
  __disable_irq();
  /* Critical Section */
  __set_PRIMASK(primask);
  ```

## 5. Project Structure

```text
Dev_embedded_architecture/       # Workspace root
├── .agents/                     # AI agents rules, skills, and guard scripts
│   ├── rules/                   # Workflow, STM32 standards, deep module rules
│   ├── skills/                  # Specialized runbooks (grill-me, stm32-build-verify, etc.)
│   └── scripts/                 # Build and guard hooks
├── .vscode/                     # VS Code tasks, settings, launch configs
├── CMakeLists.txt               # User-editable top-level build configuration
├── CMakePresets.json            # CMake Presets (Debug, Release, RelWithDebInfo)
├── Core/
│   ├── Inc/                     # CubeMX generated headers (main.h, stm32f4xx_it.h)
│   ├── Src/                     # CubeMX generated sources (main.c, stm32f4xx_it.c)
│   └── User/                    # User custom modules (e.g. ring_buffer, sensors)
│       └── ring_buffer/
│           ├── ring_buffer.h
│           └── ring_buffer.c
├── Drivers/                     # STM32 HAL & CMSIS libraries (read-only)
├── cmake/
│   ├── gcc-arm-none-eabi.cmake  # Toolchain file
│   └── stm32cubemx/             # Auto-generated CMake (do not edit manually)
├── build/                       # Build output directory (e.g. build/Debug/)
└── Dev_embedded_architecture.ioc# STM32CubeMX project file
```

### Do Not Modify Manually
- `cmake/stm32cubemx/` — regenerated by STM32CubeMX
- `Drivers/` — official ST HAL and CMSIS library sources
- Outside `/* USER CODE BEGIN */` ... `/* USER CODE END */` in `Core/Src/` and `Core/Inc/`

## 6. Build, Flash & Diagnostic Commands

### Build with CMake Presets
```powershell
# Configure preset
cmake --preset Debug

# Compile firmware
cmake --build build/Debug
```

### Flash with STM32CubeProgrammer CLI
```powershell
# Flash binary over SWD and reset target
STM32_Programmer_CLI --connect port=swd --download build/Debug/Dev_embedded_architecture.elf -hardRst -rst --start
```

### Static Analysis with Cppcheck
```powershell
# Run static analysis on user modules
cppcheck --enable=warning,style,performance,portability --inline-suppr --error-exitcode=1 Core/User/
```

## 7. Quality Gates

Before any task completion or PR delivery:
- [ ] Firmware builds cleanly (`cmake --build build/Debug`) with zero errors.
- [ ] No new `cppcheck` warnings on user code.
- [ ] Autogenerated files in `cmake/stm32cubemx/` left untouched.
- [ ] User code in `Core/Src/` strictly bounded within `/* USER CODE */` blocks.
- [ ] Public header interfaces follow Deep Module principles (<= 7 public functions).
- [ ] `walkthrough.md` artifact is updated with verification logs.
